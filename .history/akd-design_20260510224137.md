# AKD 自动绘图软件 — 设计规格说明

**日期**: 2026-05-10 
**技术栈**: TypeScript + Vue 3 + Electron  
**模块系统**: 100% ESM（零 CommonJS）  
**基于**: Anime2Sketch 开源项目（线稿提取核心）

---

## 一、产品概述

AKD 是一款桌面自动绘图工具。用户导入动漫/插画风格图片，软件提取线稿并转换为可绘制路径，通过模拟鼠标操作在其他软件（Photoshop、SAI、Clip Studio 等）中自动绘制出线稿。

### 1.1 核心术语

| 术语 | 定义 |
|------|------|
| **全局路径包围盒** | 所有路径在原图坐标系下的整体最小外接矩形，左上角为 (minX, minY)，尺寸为 (width, height)。用于预览窗口初始尺寸和绘制坐标转换 |
| **原图坐标系** | 以图片左上角为原点 (0, 0)，X 轴向右、Y 轴向下，单位为像素。提取的所有路径坐标均在此坐标系下，范围在 [0, 图片宽度] × [0, 图片高度] 内 |
| **轮廓（Contour）** | 二值图中白色线条区域的外边界像素序列，由 OpenCV `findContours` 以 `CHAIN_APPROX_NONE` 模式提取，保留全部边缘像素点。每条轮廓即为一条自然连接的绘制路径 |

## 二、用户流程

1. 启动 AKD → 系统托盘图标 + 主窗口同时出现
2. 在主窗口中导入图片（文件选择或拖拽）
3. 软件展示原图与线稿对比，后台完成路径提取
4. 用户切换到目标绘图软件
5. 按 preview 快捷键进入预览模式 → 半透明叠加窗口出现在屏幕中央，大小与绘制尺寸一致，带虚线边框，始终置顶
6. 按住 Ctrl 拖拽移动窗口位置，按住 Ctrl 拖拽四角等比缩放窗口（绘制尺寸同步变化）
7. 按 startDraw 快捷键开始绘制 → 鼠标自动跳至首条路径起点，按住鼠标沿路径移动，绘制大小与当前叠加窗口大小一致
8. 按 stopDraw 快捷键立即停止绘制并抬笔

## 三、系统架构

### 3.1 三层进程

```
Renderer (Vue 3)
  ├── 图片面板（原图 + 线稿对比）
  ├── 设置面板（快捷键、速度、透明度）
  └── 导出对话框（PNG）
        ↕ IPC
Main Process
  ├── 窗口管理（主窗口、预览叠加层）
  ├── 系统托盘管理器
  ├── 全局状态机（五状态流转）
  ├── 快捷键管理器（按状态动态注册热键）
  ├── 绘制引擎（路径队列管理、nut.js 异步鼠标模拟）
  ├── 设置存储（electron-store，便携化）
  └── IPC 处理器
        ↕ parentPort (worker_threads)
Worker Threads
  ├── 推理 Worker（ONNX Runtime，图片→线稿灰度图）
  └── 路径提取 Worker（OpenCV.js，线稿灰度图→DrawPath[]）
        ├─ 二值化（cv.threshold）+ 反转（cv.bitwise_not）
        ├─ findContours（RETR_LIST + CHAIN_APPROX_NONE）像素级轮廓提取
        ├─ approxPolyDP 轮廓简化（可选，epsilon 容差控制）
        └─ 绘制顺序优化（按路径首点空间排序）
```

### 3.2 模块职责

| # | 模块 | 位置 | 职责 |
|---|------|------|------|
| 1 | 主窗口 | Renderer | Vue 3 UI：双图对比、设置、导出 |
| 2 | 预览叠加窗口 | Main | 透明置顶、屏幕中央出现、Ctrl+拖拽移动、四角等比缩放、虚线边框、Canvas 渲染路径 |
| 3 | 系统托盘 | Main | 后台运行、右键菜单（打开主窗口/状态/导出/退出） |
| 4 | 推理 Worker | Worker | ONNX Runtime 加载模型、CPU 推理 |
| 5 | 路径提取 Worker | Worker | OpenCV.js 二值化 + findContours（RETR_LIST + CHAIN_APPROX_NONE）像素级轮廓提取 + approxPolyDP 简化 + 绘制顺序优化 |
| 7 | 绘制引擎 | Main | 路径队列管理、nut.js 异步鼠标模拟、恒速绘制 |
| 8 | 全局状态机 | Main | 五状态流转（NOT_READY/IDLE/PREVIEWING/DRAWING/ERROR） |
| 9 | 快捷键管理器 | Main | 按全局状态机当前状态动态注册/注销热键 |
| 10 | 设置存储 | Main | electron-store 持久化到 `{app}/config.json` |

### 3.3 数据流

```
用户选图 → Renderer → IPC → Main → Worker(推理)
                                        ↓ 线稿灰度图
                              Main ← Worker
                             ↙         ↘
                    Renderer(展示)   Worker(路径提取: OpenCV.js)
                              │       ├─ cv.threshold 二值化
                              │       ├─ cv.bitwise_not 反转
                              │       ├─ cv.findContours(RETR_LIST, CHAIN_APPROX_NONE)
                              │       ├─ cv.approxPolyDP 简化
                              │       └─ 绘制顺序优化（首点空间排序）
                                          ↓ DrawPath[]（原图坐标系）
                              Main ← Worker
                              │ (计算全局路径包围盒)
                             ↙         ↘
                PreviewOverlay      DrawingEngine(待startDraw触发)
                (原图坐标→屏幕坐标   (捕获叠加层位置/尺寸 →
                 渲染路径+虚线边框)    原图坐标→屏幕坐标 → 绘制)
```

### 3.4 ESM 模块架构（100% ESM，零 CommonJS）

AKD 全项目强制采用 ESM（ECMAScript Modules），**禁止使用 CommonJS（`require`/`module.exports`/`__dirname`/`__filename`）**。这一决策贯穿所有代码层：Main Process、Worker Threads、Renderer、Shared 共享层。唯一的 CJS 容忍区是极少数无法提供 ESM 入口的第三方依赖（见 §3.4.6）。

#### 3.4.1 总则：`"type": "module"` + 三层模块策略

`package.json` 声明 `"type": "module"`，全局默认 `.js` 文件为 ESM。三层 TypeScript 编译配置各有分工：

| 层 | tsconfig | module | moduleResolution | 原因 |
|----|----------|--------|-----------------|------|
| Main Process | `tsconfig.main.json` | `NodeNext` | `nodenext` | 运行于 Node.js，需原生 ESM 支持与 `node:` 协议 |
| Worker Threads | `tsconfig.worker.json` | `NodeNext` | `nodenext` | 同 Main Process，`worker_threads` 为 Node API |
| Renderer (Vue) | `tsconfig.renderer.json` | `ESNext` | `bundler` | Vite 打包，`bundler` 解析器可省略文件扩展名 |
| Shared | `tsconfig.shared.json` | `NodeNext` | `nodenext` | 被 Main/Worker 消费，需与消费方模块系统兼容 |

#### 3.4.2 导入规范：强制规则

**（A）`node:` 协议 — Node.js 内置模块**

```typescript
// ✅ 正确
import { readFile } from 'node:fs/promises';
import { resolve } from 'node:path';
import { fileURLToPath } from 'node:url';
import { parentPort } from 'node:worker_threads';

// ❌ 禁止
import { readFile } from 'fs';
import path from 'path';
```

**（B）相对导入必须带 `.js` 扩展名**

Node.js ESM 规范要求相对导入显式写出文件扩展名。TypeScript `NodeNext` 模式下 `.ts` 源文件中写 `.js` 后缀，编译器保留原样输出：

```typescript
// ✅ 正确 — NodeNext 模式，.ts 中写 .js
import { PipelineOrchestrator } from './pipeline-orchestrator.js';
import { AppState, DrawPath } from '../shared/types.js';

// ❌ 禁止 — 裸说明符在 NodeNext 下解析失败
import { PipelineOrchestrator } from './pipeline-orchestrator';
```

例外：Renderer 层使用 `moduleResolution: "bundler"`，Vite 在打包阶段自动解析扩展名，允许省略 `.js` 后缀（但不禁止写 `.js`）。Shared 层若被 Renderer 引用（通过 Vite），Vite 亦自动处理。

**（C）`import.meta.url` 替代 `__dirname` / `__filename`**

```typescript
// ✅ 正确
import { fileURLToPath } from 'node:url';
import { dirname } from 'node:path';

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

// ❌ 禁止 — __dirname / __filename 在 ESM 中不存在
const dir = __dirname;
```

**（D）动态 `import()` 用于条件加载和异步依赖**

```typescript
// ✅ 正确 — Worker 启动时按需加载大体积 WASM 包
const cv = await import('@techstark/opencv-js');

// ✅ 正确 — 条件加载（仅 Windows 需要特定模块）
if (process.platform === 'win32') {
  const { setAppUserModelId } = await import('./windows-utils.js');
}
```

**（E）禁止项清单**

| 禁止 | 原因 | 替代 |
|------|------|------|
| `require('xxx')` | CJS 专属，ESM 中不可用 | `import` / `await import()` |
| `module.exports =` | CJS 专属 | `export default` / `export const` |
| `__dirname` | CJS 专属，ESM 中不存在 | `dirname(fileURLToPath(import.meta.url))` |
| `__filename` | CJS 专属 | `fileURLToPath(import.meta.url)` |
| `import xxx from 'fs'` | 缺少 `node:` 协议 | `import xxx from 'node:fs'` |
| 相对导入省略 `.js` | NodeNext 规则要求显式扩展名 | 加上 `.js` 后缀 |

#### 3.4.3 Worker Threads ESM 加载

Node.js 的 `worker_threads` 在 `"type": "module"` 下支持直接加载 ESM Worker：

```typescript
// Main Process 创建 ESM Worker
import { Worker } from 'node:worker_threads';

const worker = new Worker(
  new URL('../workers/path-extraction/worker.js', import.meta.url),
  { workerData: { imageBuffer } }
);
```

- `new URL(..., import.meta.url)` 确保 Worker 脚本路径相对当前文件正确解析（不受 CWD 影响）
- Worker 脚本本身也受 `"type": "module"` 影响，可直接使用 `import` / `await import()` / 顶层 `await`
- esbuild 构建 Worker 时使用 `format: 'esm'`，平台 `platform: 'node'`，输出合法 Node.js ESM

#### 3.4.4 构建工具 ESM 配置

**esbuild**（主进程 & Worker 编译）：

```javascript
// scripts/build-node.mjs — 自身即为 .mjs ESM 文件
import * as esbuild from 'esbuild';

await esbuild.build({
  format: 'esm',        // 输出 ESM
  platform: 'node',
  target: 'node20',
  external: [
    'electron',
    'onnxruntime-node',
    '@techstark/opencv-js',
    // 所有 Node.js 内置模块使用 node: 协议
    'node:worker_threads', 'node:fs', 'node:path', 'node:url',
    'node:os', 'node:crypto', 'node:events', 'node:util',
  ],
});
```

**Vite**（渲染进程）：

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';

export default defineConfig({
  plugins: [vue()],
  build: {
    target: 'esnext',
    modulePreload: false,  // Electron 渲染进程无需 modulepreload
  },
});
```

#### 3.4.5 与旧方案对照

| 维度 | 旧方案（混用） | 新方案（100% ESM） |
|------|-------------|-----------------|
| package.json | 无 `"type"` 声明 | `"type": "module"` |
| Main/Worker 模块 | ESModule 混 CJS `require` | `NodeNext` + 纯 ESM |
| Node 内置模块导入 | `import ... from 'fs'` | `import ... from 'node:fs'` |
| 相对路径 | 缺扩展名，依赖工具解析 | 显式 `.js` 后缀 |
| __dirname | 随处使用 | `import.meta.url` + `fileURLToPath` |
| Worker 加载 | `new Worker('./worker.js')` | `new Worker(new URL('./worker.js', import.meta.url))` |
| 动态加载 | `require()` + 同步 | `await import()` + 异步 |

#### 3.4.6 CommonJS 隔离策略（CJS Adapter 层）

极少数第三方依赖可能**只**提供 CJS 入口（如旧版 `electron-store`）。对于这些依赖，**禁止在业务代码中直接使用 CJS 互操作语法**。改为在单一文件中封装 Adapter，对外暴露 ESM 接口：

```typescript
// src/main/store-adapter.ts — 唯一的 CJS→ESM 桥接点
import { createRequire } from 'node:module';

const require = createRequire(import.meta.url);
const Store = require('electron-store');

export const store = new Store({ ... });

// 其他文件正常 ESM 导入
import { store } from './store-adapter.js';
```

原则：
- `createRequire` 仅限于 Adapter 文件内使用
- 每个需 CJS 桥接的依赖一个 Adapter 文件，放在 `src/main/adapters/` 下
- 若依赖提供了 ESM 包装器或替代品，优先升级依赖而非新增 Adapter
- `package.json` 中记录需桥接的依赖清单，定期审查是否有 ESM 版本发布

#### 3.4.7 代码审查 ESM 检查项

每次 Code Review 必须验证：

- [ ] 无 `require()` 调用（Adapter 文件除外）
- [ ] 无 `module.exports`
- [ ] 无 `__dirname` / `__filename` 直接使用
- [ ] Node.js 内置模块使用 `node:` 协议
- [ ] 相对导入（Main/Worker/Shared 层）包含 `.js` 扩展名
- [ ] Worker 创建使用 `new URL(..., import.meta.url)` 模式
- [ ] `package.json` 中无 CJS-only 的新增依赖（如不可避免，需先建 Adapter）

### 4.4 主窗口布局

- **默认尺寸**: 960 × 680 px（最小 720 × 480 px）
- **结构**: 自定义标题栏 (32px) → 左导航 (48px) + 内容区 → 状态栏 (28px)

#### 4.4.1 左侧导航栏

48px 宽图标式导航，图标 20×20px 垂直排列：图片面板 / 设置面板 / 关于（底部固定）。激活项左侧 2px 主色竖条 + 图标变主色。

#### 4.4.2 图片面板

左右双图对比布局：
- **左侧**: 原图展示区，支持拖拽导入（png/jpg/jpeg/webp/bmp）

- **空状态**: 虚线占位框 + 图标 + "拖拽图片到此处或点击选择文件"
- **底部操作栏**: [导入图片] 主按钮 + [导出线稿 PNG] 次按钮
- **处理中**: 线稿区显示脉冲骨架屏动画

### 4.5 预览叠加窗口

#### 4.5.1 视觉设计

- 窗口属性: `transparent: true`, `alwaysOnTop: true`, `frame: false`
- 虚线边框: 2px `[4, 4]`，颜色可配
- 路径线条: Canvas 2D 渲染，2px 物理像素，抗锯齿
- 整体透明度: 0.6（可调 0.3~0.8）
- 初始尺寸 = 全局路径包围盒尺寸，屏幕中央出现

#### 4.5.2 交互

| 操作 | 行为 |
|------|------|
| 默认状态 | 鼠标穿透 (`setIgnoreMouseEvents(true)`) |
| 按住 Ctrl | 鼠标事件恢复，可拖拽移动，四角出现 8×8px 缩放手柄 |
| 四角拖拽 | 等比缩放 (0.5x~3.0x)，实时重绘 Canvas，显示浮动尺寸标签 |
| 松手 | 轻微弹性回弹 (400ms) |

#### 4.5.3 技术要求

- Windows 上 Ctrl + `setIgnoreMouseEvents` 切换需提前 50ms 在 keydown 中处理
- 缩放时 Canvas 重绘做 `requestAnimationFrame` 帧节流
- 不使用毛玻璃 blur（透明窗口性能开销大），纯透明背景即可

| **快捷键键帽** | `--color-surface-300` 底，模拟键盘立体感，等宽 11px |
| **状态指示灯** | 8px 圆点 + Lucide 图标 + 中文标签 + 附加信息，5 状态独立配色与动画（详见 §4.7.1） |
| **Toast** | 毛玻璃背景，右上角滑入，3 秒自动消失，弹性缓动 |
| **拖拽区（空状态）** | 虚线边框 `[6,4]`，拖入时边框变主色 + 5% 主色底 |

#### 4.7.1 状态指示灯（StatusIndicator）详细规格

状态指示灯位于主窗口底部状态栏（`StatusBar.vue → StatusIndicator.vue`），实时反映全局状态机（§7）的当前状态。所有元素颜色通过根节点 `style` 绑定驱动，子元素使用 `currentColor` 继承，实现"单点切换、全链响应"。

**通用结构**：

```
[●] 状态图标  状态标签  │  附加信息
 8px圆点    Lucide 16px  12px      灰色次要文字
```

| 属性 | 规格 |
|------|------|
| 圆点尺寸 | 8px × 8px，`border-radius: 50%` |
| 圆点与图标间距 | 6px |
| Lucide 图标尺寸 | 16px，`stroke-width="1.5"`，`currentColor` |
| 图标与标签间距 | 4px |
| 状态标签字号 | 12px，`font-weight: 500`，`currentColor` |
| 分隔符 | `|`，`--color-surface-500`，与标签间距 8px |
| 附加信息字号 | 12px，`--color-surface-600` |
| 容器高度 | 28px（匹配状态栏），左右 padding 12px |
| 无障碍 | `role="status"` + `aria-live="polite"`，状态变更时屏幕阅读器自动播报 |

**5 状态视觉映射**：

| 状态 | 圆点颜色 | 动画 | 文字标签 | Lucide 图标 | 附加信息 |
|------|---------|------|---------|------------|---------|
| **NOT_READY** | `--color-info` `#60a5fa` | 脉冲呼吸 2s | 未就绪 | `CircleDashed` | 动态："等待导入图片" / "模型加载中…" / "推理中 65%" |
| **IDLE** | `--color-success` `#34d399` | 无（静态） | 空闲 | `CircleCheck` | "N 条路径就绪"（无路径时留空） |
| **PREVIEWING** | `--color-primary-500` `#6366f1` | 光晕扩散 3s | 预览中 | `Eye` | 缩放比例 "1.0x"（动态跟随预览窗缩放） |
| **DRAWING** | `--color-warning` `#fbbf24` | 脉冲呼吸 1s | 绘制中 | `PenLine` | "路径 3/15" + "速度 500px/s" |
| **ERROR** | `--color-error` `#f87171` | **静态常亮** | 错误 | `CircleX` | 具体原因："模型加载失败，请重试" |

**设计理由**：
- NOT_READY 用**信息蓝** — 系统正在工作，属正常流程，非警示色，不引起焦虑
- IDLE 用**绿色静态** — "一切就绪，请操作"，无动画 = 稳定，鼓励用户行动
- PREVIEWING 用**主色靛蓝紫** — "你已进入交互模式"，光晕强调窗口可操作
- DRAWING 用**琥珀色** — "机器正在运行"，1s 快脉冲传达"忙碌中，不要干扰"
- ERROR 用**红色静态** — 不闪烁。闪烁对光敏性用户不友好，静态红已足够引起注意

**CSS 动画定义**：

```css
/* 脉冲呼吸 — NOT_READY (2s) / DRAWING (1s) */
@keyframes status-pulse {
  0%, 100% { opacity: 1; }
  50%      { opacity: 0.35; }
}

/* 光晕扩散 — PREVIEWING (3s) */
@keyframes status-glow {
  0%, 100% { box-shadow: 0 0 0 0 rgba(99, 102, 241, 0); }
  50%      { box-shadow: 0 0 0 4px rgba(99, 102, 241, 0.3); }
}
```

**TypeScript 接口**：

```typescript
enum StatusState {
  NOT_READY  = 'NOT_READY',
  IDLE       = 'IDLE',
  PREVIEWING = 'PREVIEWING',
  DRAWING    = 'DRAWING',
  ERROR      = 'ERROR',
}

interface StatusConfig {
  color:     string   // CSS 变量
  icon:      string   // lucide 组件名
  label:     string   // 中文标签
  animation: 'none' | 'pulse' | 'glow'
  ariaLabel: string   // 屏幕阅读器描述
}
```

**状态切换过渡**：圆点背景色和图标/文字颜色统一 250ms `ease-in-out` 过渡。动画启停时 150ms `ease-out` 淡入淡出，避免生硬闪烁。

#### 4.14.1 图标库：lucide-vue-next

#### 4.14.2 字体方案：@fontsource npm 自托管

**选型结论**：采用 `@fontsource/inter` + `@fontsource/jetbrains-mono`，中文字体走系统回退。

**选择理由**：

1. **Electron 离线优先** — 桌面应用不应依赖外部 CDN，用户可能在无网环境使用
2. **隐私零顾虑** — Google Fonts 会向 Google 发送 DNS/HTTP 请求，作为桌面软件不妥
3. **版本可控** — npm 锁定版本，不会因 CDN 推送更新导致 UI 渲染突变
4. **子集化轻量** — 仅加载所需字重（Inter 400/500/600 + JetBrains Mono 400/500），总体积 ~180~220KB

**中文字体策略**：不打包中文字体（单个中文字体 5~15MB）。使用 CSS font-family 链式回退至系统字体：

```css
--font-ui:   'Inter', 'Microsoft YaHei', 'PingFang SC', system-ui, sans-serif;
--font-mono: 'JetBrains Mono', 'Cascadia Code', 'Consolas', monospace;
```

| 平台 | UI 中文回退字体 | 等宽回退字体 |
|------|---------------|------------|
| Windows | 微软雅黑 | Consolas |
| macOS | 苹方 (PingFang SC) | SF Mono |
| Linux | 系统 sans-serif | 系统 monospace |

**依赖**：

```json
"@fontsource/inter": "^5.0.0",

```

## 五、预览叠加窗口

### 5.1 窗口属性

- `transparent: true`, `alwaysOnTop: true`, `frame: false`
- `setIgnoreMouseEvents(true)` — 默认状态下所有鼠标事件穿透至下层目标软件
- 初始大小 = 全局路径包围盒尺寸（与绘制内容 1:1 对应）
- 整体 `opacity: 0.6`（可配置 0.3~0.8）

### 5.2 生命周期

- 按 preview 快捷键：以全局路径包围盒尺寸创建叠加窗口，出现在屏幕正中央
- 再按 preview 快捷键：销毁窗口，退出预览

### 5.3 移动

按住 Ctrl 键时：
- `setIgnoreMouseEvents(false)` — 窗口临时接收鼠标事件
- 在窗口内任意位置拖拽即可移动窗口
- 松开 Ctrl 键：`setIgnoreMouseEvents(true)` — 恢复鼠标穿透

### 5.4 缩放（四角等比拉伸）

按住 Ctrl 键时，叠加窗口四角出现 ±8px 热区：
- 鼠标进入热区后光标变为对角线箭头（如 `nw-resize`）
- 拖拽任意一角，窗口等比缩放（锁定宽高比）
- 缩放过程中实时重新渲染 Canvas
- 松开 Ctrl 键：恢复鼠标穿透

缩放范围：0.5x ~ 3.0x（相对于全局路径包围盒尺寸）。无滚轮缩放。

### 5.5 虚线边框

- 窗口边缘绘制 2px 虚线边框（`[4, 4]` 虚线间隔）
- 边框颜色默认 `#000000`，与叠加线条色共用配置项
- 边框始终可见，不参与绘制内容

### 5.6 Canvas 渲染

- 路径点序列 stroke 渲染（逐点连线），线宽 2px 物理像素，抗锯齿开启
- 渲染区域 = 窗口客户区（边框内侧），坐标系映射同 §9.2

### 5.7 多显示器

叠加窗口默认出现在主屏幕中央。用户可将窗口拖拽至任意屏幕。

## 七、全局状态机

状态机是 AKD 的核心控制中枢，所有模块的行为均受当前状态约束。状态机独立于任何 UI 组件或快捷键逻辑，仅负责状态流转与进入/退出时触发的副作用。

### 7.1 状态定义

| 状态 | 含义 | 进入条件 | 前置条件 |
|------|------|----------|----------|
| **未就绪（NOT_READY）** | 未导入图片或路径提取未完成 | 启动完成 / 导入的图片正在处理中 | — |
| **空闲（IDLE）** | 路径提取完成、等待操作 | 路径提取完成 / 绘制完毕 / stopDraw 停止后 | DrawPath[] 存在 |
| **预览中（PREVIEWING）** | 叠加窗口显示在屏幕中央，可 Ctrl+拖拽移动和四角缩放 | preview 从空闲进入 | 空闲状态 |
| **绘制中（DRAWING）** | 鼠标模拟正在执行 | startDraw 从预览中进入 | 预览中状态 |
| **错误（ERROR）** | 发生需人工介入的致命错误，所有功能锁定 | 任意状态转入（见 7.2） | — |

### 7.2 ERROR 状态详规

#### 进入条件（从任意状态转入）

以下任一情况发生时，立即进入 ERROR：

1. ONNX 模型加载失败
2. 推理超时（>30s）
3. OpenCV WASM 加载失败
4. 路径提取失败（findContours 异常 / Worker 异常）
5. 无有效线条（findContours 返回空或全部轮廓 < 3 点）

#### 进入时立即执行的副作用

| 副作用 | 说明 |
|--------|------|
| 热键全部注销 | 调用 `globalShortcut.unregisterAll()`，屏蔽所有快捷键输入 |
| 绘制引擎强制停止 | 若当前为 DRAWING，立刻 `mouse.releaseButton()` + 清空绘制队列 + 设置 `stopFlag = true` |
| 预览窗口销毁 | 若存在叠加窗口，调用 `PreviewOverlay.destroy()` |
| Worker 清理 | 终止所有进行中的 `worker_threads`（`worker.terminate()`） |
| UI 同步 | 通过 IPC `app-state` 推送 ERROR → 状态灯红色常亮、图片面板显示错误提示覆盖层、所有操作按钮置灰 |
| 系统通知 | 托盘弹出对应错误描述通知（见 §13） |

#### 退出条件（唯一出口）

ERROR 不可自动恢复。用户必须在 UI 错误提示覆盖层上点击 **[重试]** 按钮：

1. **重置状态机**：状态切回 `NOT_READY`
2. **清理缓存数据**：清空当前图片 Buffer、`DrawPath[]`、`BoundingBox`
3. **重新初始化关键资源**：重新加载 ONNX 模型
   - 若模型加载成功 → 状态保持在 `NOT_READY`，等待用户导入新图片
   - 若模型加载又失败 → 再次进入 `ERROR`，形成循环直到成功或用户退出
4. **UI 恢复**：移除错误覆盖层，恢复所有操作按钮入口

### 7.3 中断与新图片导入

除 `ERROR` 外，任何状态下用户导入新图片：

- **导入失败**（取消选择、格式不支持、文件损坏无法读取）：不做任何回退，保持当前状态，托盘通知用户导入失败原因
- **导入成功**：执行以下流程：

1. 若在 `DRAWING`：立即停止绘制（同 stopDraw），抬笔
2. 若在 `PREVIEWING`：销毁叠加窗口
3. 取消所有进行中的 Worker（推理/路径提取）
4. 进入 `NOT_READY`
5. 自动开始新的推理管线（推理 → 路径提取）
6. 管线全部完成后自动进入 `IDLE`，主窗口展示新线稿与原图对比
7. 若任何步骤失败（推理/路径提取），进入 `ERROR`

### 7.4 安全策略

- **鼠标模拟**：仅 `DRAWING` 状态激活，退出绘制后立即终止
- **Ctrl 键监听**：仅 `PREVIEWING` 状态监听 Ctrl 按下/释放，退出预览后立即注销
- **应用退出保护**：`app.on('before-quit')` 中若为 `DRAWING`，先执行 stopDraw 抬笔 → 再 `app.quit()`
- **状态变更原子性**：状态切换操作不可中断，副作用（热键注册/注销、窗口创建/销毁）按顺序完整执行

## 八、快捷键管理器

快捷键管理器独立于状态机，职责单一：**监听状态机变更 → 按当前状态注册/注销对应热键**。

### 8.1 各状态可用热键

| 热键 | NOT_READY | IDLE | PREVIEWING | DRAWING | ERROR |
|------|-----------|------|------------|---------|-------|
| preview | ❌ | ✅ 进入预览 | ✅ 退出预览 | ❌ | ❌ |
| startDraw | ❌ | ❌ | ✅ 开始绘制 | ❌ | ❌ |
| stopDraw | ❌ | ❌ | ❌ | ✅ 立即停止并抬笔 | ❌ |

### 8.2 工作原理

1. 状态机每次完成状态转换后，发送状态变更事件
2. 快捷键管理器接收新状态 → 调用 `globalShortcut.unregisterAll()` → 按上表注册新状态对应的热键
3. `NOT_READY` 和 `ERROR` 状态下不注册任何热键
4. 用户修改快捷键配置（通过设置面板）→ 触发 `update-settings` → 若当前状态已有注册的热键 → 自动注销并重新按新键值注册

### 8.3 安全约束

- 热键回调内部必须先检查当前状态机状态是否与注册时一致（防止竞态）
- `globalShortcut.register` 失败（如被其他应用占用）→ 托盘通知用户冲突，不阻塞状态流转
- 应用失去焦点时不注销热键（全局热键跨应用有效）

## 九、绘制引擎

### 9.1 流程

startDraw 触发 → 捕获当前预览叠加层的屏幕位置与窗口尺寸 → 关闭叠加层 → 鼠标跳至首条路径起点 → 按住按键 → 沿路径点序列异步移动 → 抬笔 → 下一条 → 完成 → 托盘通知用户绘制完毕

### 9.2 坐标转换

路径坐标均在原图坐标系下（见 §1.1）。startDraw 触发时，根据叠加窗口当前的屏幕位置和尺寸计算缩放因子，将每条路径的每个点转换为屏幕绝对坐标：

```
缩放因子 = 叠加窗口当前尺寸 / 全局路径包围盒尺寸
屏幕坐标 = 叠加窗口屏幕位置 + (路径点原图坐标 - 全局路径包围盒左上角) × 缩放因子
```

缩放因子在 X 和 Y 方向上使用较大的一方（等比缩放，保持宽高比）。绘制结果大小与叠加窗口当前大小一致。

### 9.3 路径点序列

路径提取 Worker 输出的每条路径为轮廓像素级坐标点序列（`{x, y}[]`），由 `findContours` + `CHAIN_APPROX_NONE` 提取，已保留全部边缘像素——轮廓点在空间上自然连续连接，无需额外插值或方向匹配。按绘制速度换算步进延迟后逐点移动鼠标。默认步进 1 像素/步，步进延迟 = 1 / 绘制速度（秒）。

### 9.4 异步绘制循环

绘制循环强制采用异步非阻塞方式：

```
async function drawPath(path, speed):
  for each point in path:
    screenPoint = toScreen(point)
    moveMouse(screenPoint)
    await delay(步进延迟)
    if stopFlag: break  // stopDraw 立即响应
```

- `delay` 使用 `setTimeout` 封装的 Promise
- 每步检查 `stopFlag`，确保 stopDraw 即时生效

### 9.5 路径队列

绘制引擎按路径提取 Worker 输出的顺序逐个消费 `DrawPath`（排序已由 Worker 完成，见 §12.3 步骤 4）。

### 9.6 鼠标模拟

- 通过 `@nut-tree-fork/nut-js` 跨平台鼠标控制库实现（主进程调用）

### 9.7 按键

- 左键或右键（用户设置）
- 路径间抬笔→异步移动到下一条起点→落笔
- stopDraw：在下一个步进检查点立即抬笔 + 停止

### 9.8 速度

恒速模式，像素/秒（100~2000），用户设置

## 十一、推理管线

### 11.1 流程

原始图片 → 预处理 → ONNX Runtime 推理 → 后处理 → 线稿位图 → 内存

### 11.2 预处理

- 直接缩放至 512×512 正方形（`fit: 'fill'`，不保持宽高比），与 Anime2Sketch `transforms.Resize([512, 512], BICUBIC)` 一致
- RGB 通道，归一化 `(pixel/255 - 0.5) / 0.5` → [-1, 1]
- 张量格式：(1, 3, 512, 512) NCHW float32

### 11.3 推理

- `onnxruntime-node` 在 Worker Thread 中运行
- 加载 `resources/models/anime2sketch.onnx`
- `executionProviders: ['cpu']`
- 输出：(1, 1, 512, 512) 灰度张量

### 11.4 后处理

- 反归一化：`(tensor + 1) / 2 * 255` → [0, 255] 连续灰度
- 缩放至原始尺寸（bicubic-like），与 Anime2Sketch `tensor_to_img` + PIL `resize` 一致
- 二值化由路径提取 Worker 在 findContours 前完成，推理管线输出保留完整灰度信息
- 输出：灰度 PNG Buffer（内存中，供 UI 展示和路径提取 Worker 消费）

### 11.5 模型加载

- 应用启动时预加载到内存，托盘 tooltip 显示"加载中..."
- 加载失败：托盘通知用户，禁用推理功能

### 11.6 模型来源

`resources/models/`目录下的onnx权重文件

## 十二、路径提取

### 12.1 核心思想：像素级轮廓追踪

采用与 SlaytheSpire2Drawing.py 相同的技术路线——**跳过骨架化与拓扑分析，直接用 OpenCV `findContours` + `CHAIN_APPROX_NONE` 从二值化线稿中提取像素级轮廓路径**。

**为什么可行**：

推理 Worker 输出的线稿灰度图中，线条为暗色像素（~0）、背景为亮色（~255）。反转后线条变为白色前景区域、背景变黑。`findContours` 将每条白色线条区域的边界提取为一个完整的像素序列——这个序列本身就是一条自然的、空间连续的绘制路径。轮廓点沿着线条边界依次排列，无需额外的方向匹配或路径重建。

**相比旧方案的简化**：

| 旧方案（骨架化+拓扑） | 新方案（findContours） |
|----------------------|----------------------|
| Guo-Hall 骨架化 → 单像素骨架 | 二值化 + 反转，直接找轮廓 |
| BFS 连通分量提取 + 连接数分析 | findContours 天然分离每条轮廓 |
| 端点/交叉点分类 + 拓扑追踪 | 轮廓点序列已是完整的绘制路径 |
| @thi.ng/vectors 方向一致性匹配 | 轮廓点天然沿边界有序排列 |
| 路径重建（端点→交叉点拼接） | 无——轮廓即路径 |
| @thi.ng/geom-resample DP 简化 | approxPolyDP 一步完成 |

### 12.2 流程

```
线稿灰度图 → 二值化(cv.threshold) → 反转(cv.bitwise_not) → findContours(RETR_LIST, CHAIN_APPROX_NONE)
                                                                      ↓
                                                             轮廓点序列(像素级)
                                                                      ↓
                                                       approxPolyDP 简化（可选）
                                                                      ↓
                                                          绘制顺序优化 → DrawPath[]
```

### 12.3 路径提取 Worker（OpenCV.js）

全部路径提取工作在单个 Worker Thread 中完成：

**步骤 1：二值化 + 反转**
- 调用 `cv.threshold(gray, binary, 128, 255, cv.THRESH_BINARY)` 将灰度线稿二值化
- 调用 `cv.bitwise_not(binary, inverted)` 反转——线条变为白色（255）前景区域，背景为黑色（0）。白色区域即为 `findContours` 的检索目标
- 阈值 128 为默认值，可根据线稿质量通过"精细度"滑块微调（范围 64~192）

**步骤 2：像素级轮廓提取 — `findContours`**
- 调用 `cv.findContours(inverted, contours, hierarchy, cv.RETR_LIST, cv.CHAIN_APPROX_NONE)`
- `RETR_LIST`：提取所有轮廓，不建立父子层级关系。每条线条独立为一个轮廓
- `CHAIN_APPROX_NONE`：**不做任何压缩**，存储轮廓上的每一个像素点。这是像素级精度的核心——与 SlaytheSpire2Drawing.py 完全一致
- 输出：`contours` 为 `cv.MatVector`，每个 `cv.Mat` 的 shape 为 (N, 1, 2)，N 为轮廓像素数，每点 (x, y) 为整数像素坐标
- 至此已获得可直接绘制的路径数组——轮廓点空间连续、方向有序，无需再经过方向匹配或路径重建

**步骤 3：approxPolyDP 轮廓简化（可选）**
- 调用 `cv.approxPolyDP(contour, approx, epsilon, false)` 对每条轮廓执行 Douglas-Peucker 近似
- `false` = 开放路径（不强制闭合），保持线条端点位置不变
- `epsilon`：简化容差，默认 1.0 像素。epsilon 越大路径点数越少、绘制越快；epsilon 越小精度越高
- 简化后仍保持轮廓的像素级坐标序列 `{x, y}[]`

**步骤 4：绘制顺序优化**
- 按路径首点空间位置排序：优先比较 Y 坐标，Y 相同时比较 X（升序）
- 排序确保绘制过程遵循从上到下、从左到右的习惯，减少鼠标跨屏幕大幅跳跃

**步骤 5：输出**
- 返回最终的 `DrawPath[]`（`{x, y}[]` 坐标点数组），所有路径坐标均位于原图坐标系下
- Worker 返回后，主进程计算全局路径包围盒（所有路径点的最小外接矩形）

### 12.4 关键参数

| 参数 | 默认值 | 范围 | 说明 |
|------|--------|------|------|
| 二值化阈值 | 128 | 64~192 | 控制线条粗细感知，对应 UI "精细度"滑块 |
| approxPolyDP epsilon | 1.0 | 0.5~3.0 | 简化容差，对应 UI "绘制速度"滑块（间接影响） |

### 12.5 边界情况

| 场景 | 处理 |
|------|------|
| 无轮廓（全白或全黑） | `findContours` 返回空数组 → 触发 ERROR（"未检测到可绘制线条"） |
| 极小轮廓（< 3 点） | 过滤丢弃，低于 3 个像素点的轮廓无法形成有效绘制 |
| 线稿线条过粗（>5px） | `findContours` 沿线条外边界提取轮廓，绘制时轮廓边界仍可正确追踪。若需更细路径，可提高二值化阈值或增加前置的 Canny 边缘检测 |

### 12.6 @techstark/opencv-js 加载与使用注意事项

AKD 的 OpenCV 运行在 Node.js Worker Thread 中（`worker_threads`），而非浏览器渲染进程，因此其加载方式与 Webpack/Vite 浏览器场景**有所不同**。

#### 12.6.1 初始化：await 异步加载（v4.11+）

`@techstark/opencv-js` v4.11+ 默认导出 `cvReadyPromise`，使用 WebAssembly 编译，初始化是异步的。Worker 中必须等待加载完成后再调用任何 OpenCV 函数：

```typescript
import cvReadyPromise from '@techstark/opencv-js';

async function initOpenCV() {
  const cv = await cvReadyPromise;
  // cv.threshold、cv.findContours 等现在可用
  return cv;
}
```

注意：旧版 `cv.onRuntimeInitialized` 回调方式在 v4.11+ 中已不推荐，统一使用 `await`。

#### 12.6.2 TypeScript 配置

Worker 的 `tsconfig.worker.json` 使用 `"module": "NodeNext"` + `"moduleResolution": "nodenext"`。`@techstark/opencv-js` 自带了 TypeScript 类型定义（由 mirada 项目自动生成），无需额外安装 `@types/` 包。`NodeNext` 模块解析下直接 `import` 即可：

```typescript
import cvReadyPromise from '@techstark/opencv-js';
// 或使用类型：
import type { OpenCV } from '@techstark/opencv-js';
```

已知限制：自动生成的类型定义可能不完全准确（例如部分函数签名与运行时行为存在偏差），遇到类型报错时优先以 OpenCV.js 官方文档的运行时行为为准。

#### 12.6.3 Worker Thread 环境：无需 Vite/Webpack 回退配置

关键事实：OpenCV 运行在 Node.js Worker Thread 中，**不经过 Vite 打包**（Worker 由 `tsconfig.worker.json` 独立编译为 Node.js 目标代码）。

- `fs`、`path`、`crypto` 是 Node.js 原生模块，Worker 中直接可用——无需 Webpack `resolve.fallback` 或 `vite-plugin-node-polyfills`
- WASM 文件通过 Node.js 文件系统加载，无需 `assetsInclude: ["**/*.wasm"]`
- `optimizeDeps.exclude` 仅影响 Vite 预打包，Worker 不受其约束

**唯一需要的预防措施**：确保渲染进程代码（Vue/Vite 端）不直接 import `@techstark/opencv-js`。OpenCV 的导入应仅限于 Worker 文件内。若确实需要在 Vite 端引用其类型，使用 `import type` 语法（编译后会被擦除，不产生运行时依赖）。

#### 12.6.4 WASM 加载失败处理

Worker 启动时 `await cvReadyPromise` 若抛异常（WASM 文件损坏、内存不足等），Worker 通过 `parentPort.postMessage({ type: 'error', ... })` 通知主进程，由主进程触发全局状态机进入 ERROR 状态（见 §7.2），托盘通知"路径提取引擎加载失败，请重试"。

#### 12.6.5 包版本锁定

建议锁定 `@techstark/opencv-js` 至精确版本（如 `"@techstark/opencv-js": "4.12.0-release.1"`），因为 OpenCV.js WASM 构建因 Emscripten 版本变化，在不同版本间可能存在行为差异。

## 十三、错误与边界处理

以下场景触发全局状态机进入 `ERROR`（见 §7.2），同时按场景推送对应的托盘通知：

| 场景 | 触发状态 | 托盘通知内容 |
|------|----------|-------------|
| ONNX 模型加载失败 | → ERROR | "模型加载失败，请重试" |
| 推理超时 (>30s) | → ERROR | "推理超时，请重试" |
| OpenCV WASM 加载失败 | → ERROR | "路径提取引擎加载失败，请重试" |
| 路径提取失败（findContours/Worker 异常）| → ERROR | "路径提取失败，建议换图" |
| 无有效线条（findContours 返回空） | → ERROR | "未检测到可绘制线条" |

以下场景为**非致命边界情况**，不触发 ERROR，仅做本地处理：

| 场景 | 行为 |
|------|------|
| 非图片文件 | 文件选择器过滤，仅接受支持格式 |
| 导入文件损坏/无法读取 | 托盘通知用户导入失败，保持当前状态 |
| 极小图片 (<100px) | 允许导入但托盘通知用户效果可能不佳 |
| 绘制中关闭应用 | `before-quit` → 先 stopDraw 抬笔再退出（见 §7.4） |
| 多实例启动 | `app.requestSingleInstanceLock()` 获取锁失败则激活已有窗口并退出当前实例 |
| 路径超出屏幕 | 仅保留屏幕内部分，超出部分丢弃 |
